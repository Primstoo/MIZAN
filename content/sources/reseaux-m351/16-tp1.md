```exercice VII.2-3 · Commande ping (capture : ping -n 10 www.google.fr)
? {n34} **7a1.** a1) Quels sont les protocoles indiqués dans la colonne Protocol ? (Les paquets ICMP sont-ils précédés de DNS ?)
indice: Colonne « Protocol » de la liste. Filtre utile : icmp || dns
= Tu dois voir surtout <b>DNS</b> puis <b>ICMP</b>. Avant de pinguer, le PC demande l'adresse IP de www.google.fr au DNS (requête puis réponse), et c'est seulement ensuite qu'il envoie les pings. D'autres protocoles de fond peuvent apparaître (ARP, TLS, TCP, UDP, QUIC, MDNS, SSDP) : c'est le trafic normal de ta machine.
? {n25} **7a2.** a2) Relever l'adresse IP renvoyée avec la réponse DNS.
indice: Filtre : dns.flags.response == 1. Dans le détail : Domain Name System (response) → Answers → www.google.fr: type A, addr …
= C'est l'enregistrement de <b>type A</b> dans « Answers » (une adresse IPv4 de Google, du type 142.250.x.x ou 216.58.x.x). Vérification : c'est la même que celle que la console affiche entre crochets \[ \] au début du ping.
? {n34} **7b1.** b1) Premier Echo Request : adresse IP destination ? Valeur du champ Protocol Type ? Valeur du champ Time To Live ?
indice: Filtre : icmp.type == 8, premier paquet. Développe « Internet Protocol Version 4 ».
= <b>Destination</b> = l'IP de Google relevée en a2.<br><b>Protocol</b> = <b>1 (ICMP)</b> : c'est ce champ de l'en-tête IP qui dit que la charge est de l'ICMP (6 = TCP, 17 = UDP).<br><b>TTL = 128</b> si tu es sous Windows (64 sous Linux ou macOS) : c'est la valeur de départ choisie par ton système.
? {n34} **7b2.** b2) Type de message ICMP ? Identificateur ? Numéro de séquence ?
indice: Développe « Internet Control Message Protocol ».
= <b>Type 8 (Echo request), code 0</b>.<br><b>Identifier</b> : un numéro fixe pour toute la commande ping (sous Windows, souvent 0x0001). Wireshark l'affiche en BE et en LE, deux ordres de lecture des octets.<br><b>Sequence number</b> : il augmente de 1 à chaque ping (10 valeurs pour -n 10).
? {n24} **7b3.** b3) Sélectionner les octets de données de la requête et les comparer avec l'affichage brut.
indice: Clique sur « Data » dans l'ICMP : les octets se surlignent dans la zone du bas (hexa + ASCII).
= Sous Windows, ping envoie <b>32 octets</b> de remplissage : abcdefghijklmnopqrstuvwabcdefghi. En hexa : 61 62 63 64… (le code ASCII de a, b, c, d…). C'est la démonstration du TP : la zone du milieu (champs décodés) et la zone du bas (octets bruts) montrent la même chose, sous deux formes.
? {n34} **7c1.** c1) Premier Echo Reply : adresses IP source et destination ? Champ Protocol Type ?
indice: Filtre : icmp.type == 0. Le premier paquet.
= Elles sont <b>inversées</b> par rapport à la requête : <b>source = Google</b>, <b>destination = ton PC</b>. Protocol = <b>1 (ICMP)</b>.
? {n34} **7c2.** c2) Valeur du champ Time To Live de la réponse ?
indice: Internet Protocol → Time to Live, dans l'Echo Reply.
= Elle est <b>plus petite qu'une valeur ronde</b> (ex. 117 ou 118). Le serveur l'a envoyée avec un TTL de départ (souvent 128 ou 64), et chaque routeur traversé a retiré 1. Estimation du nombre de sauts = la valeur de départ juste au-dessus − le TTL reçu (ex. 128 − 117 = 11 routeurs).
? {n34} **7c3.** c3) Type de message ICMP de la réponse ? Comparer l'identificateur et le numéro de séquence avec ceux de la requête.
indice: ICMP de l'Echo Reply. Wireshark ajoute un lien « \[Request frame: …\] ».
= <b>Type 0 (Echo reply), code 0</b>. L'identifiant et le numéro de séquence sont <b>identiques</b> à ceux de la requête correspondante : c'est comme ça que ping associe chaque réponse à sa requête et calcule le temps aller-retour.
? {n24} **7c4.** c4) Comparer les données de la réponse avec celles de la requête.
indice: Clique sur « Data » de l'Echo Reply.
= Les données sont <b>exactement les mêmes</b> (abcdef…). L'Echo Reply renvoie à l'identique ce qu'il a reçu, d'où le nom « écho ».
```

```exercice VII.4-5 · Commande tracert (capture : tracert www.google.fr)
? {n34} **75a1.** a1) Quels sont les protocoles indiqués dans la colonne Protocol ?
indice: Filtre : icmp || dns
= <b>DNS</b> (au début, pour l'IP de Google, puis des requêtes « PTR » pour retrouver le nom de chaque routeur) et <b>ICMP</b> : des <b>Echo Request</b> envoyés par ton PC, et des <b>Time-to-live exceeded (type 11)</b> renvoyés par chaque routeur, puis des Echo Reply du serveur final.<br>⚠ Sous Windows, tu ne verras pas d'UDP : tracert utilise ICMP. C'est traceroute, sous Linux, qui envoie de l'UDP (ports 33434 et plus), et c'est de lui que parle l'énoncé.
? {n34} **75b1.** b1) Premier paquet envoyé par tracert : adresse IP destination ? Champ Protocol Type ? Time To Live ?
indice: Filtre : icmp.type == 8 (Windows) ou udp (Linux). Le premier paquet.
= <b>Destination</b> = l'IP de Google. <b>Protocol</b> = 1 (ICMP) sous Windows, 17 (UDP) sous Linux. <b>TTL = 1</b> : c'est toute l'astuce. Le 1er routeur met le TTL à 0, détruit le paquet et répond par un ICMP Time Exceeded, ce qui révèle son adresse. Puis tracert recommence avec TTL = 2, 3… (3 paquets par valeur de TTL).
? {n34} **75b2.** b2) Comparer l'IP destination relevée avec celle de la réponse DNS. Noter les valeurs caractéristiques de l'en-tête IP.
indice: Internet Protocol du 1er paquet tracert.
= C'est <b>la même IP</b> que celle donnée par le DNS : tracert vise bien le serveur final. Seul le TTL varie d'un envoi à l'autre. Valeurs à noter : Version 4, Header length 20 octets, Protocol 1 (ou 17), TTL 1, 2, 3…, l'IP source (ton PC) et l'IP destination (Google).
? {n24} **75b3.** b3) Combien d'octets de données sont présents dans ce message de requête ?
indice: Clique sur « Data » : sa longueur est indiquée entre crochets \[Length: …\].
= Lis la valeur dans ta capture. Sous Windows, tracert envoie en général <b>64 octets</b> de données (certitude moyenne), contre 32 pour ping. Sous Linux, traceroute UDP envoie 32 octets. Vérifie avec le calcul : longueur totale IP − 20 (en-tête IP) − 8 (en-tête ICMP ou UDP) = données.
```

```exercice VIII.3-a/b · Navigation Web : trame, IP et UDP du 1er message DNS
? {n24} **8a1.** a1) Protocoles de la capture : confirmer la présence de DNS, TCP et HTTP.
indice: Filtre : dns || tcp || http || tls. Statistics → Protocol Hierarchy.
= Tu dois voir <b>DNS</b> (résolution de www.fpbm.ma), <b>TCP</b> (connexion en 3 temps) et <b>HTTP</b>. ⚠ Comme le site passe en HTTPS, tu verras surtout du <b>TLS</b>, et au mieux un seul échange HTTP : la redirection 301. Écris-le dans ton compte-rendu, puis refais la capture avec http://neverssl.com pour avoir du vrai HTTP.
? {n28} **8b1.** b1) 1er message DNS du client : adresses MAC (Ethernet) et IP du client ?
indice: Filtre : dns.flags.response == 0, premier paquet. Développe « Ethernet II » (Src) et « Internet Protocol » (Src). Vérifie avec ipconfig /all.
= <b>MAC source</b> = l'adresse physique de TA carte réseau (6 octets, ex. a4:5e:60:…). <b>IP source</b> = ton adresse locale (ex. 192.168.1.x ou 10.x.x.x). Elles doivent correspondre à « Adresse physique » et « Adresse IPv4 » dans ipconfig /all.
? {n24} **8b2.** b2) Contenu du champ Type de la trame Ethernet ?
indice: Ethernet II → Type.
= <b>0x0800 = IPv4</b>. Ce champ dit à la couche 2 quel protocole de couche 3 est transporté (0x0806 = ARP, 0x86DD = IPv6). C'est le rôle de la sous-couche LLC vu en cours.
? {n28} **8b3.** b3) Adresses MAC et IP de destination ?
indice: Ethernet II → Dst ; Internet Protocol → Dst.
= <b>MAC destination</b> = la MAC de ta <b>passerelle</b> (la box ou le routeur), pas celle du serveur DNS. <b>IP destination</b> = celle du <b>serveur DNS</b> (souvent l'IP de la passerelle elle-même, ou un DNS public comme 8.8.8.8, ou celui de la fac). Vérifie dans ipconfig /all, ligne « Serveurs DNS ».
? {n34} **8b4.** b4) À quelles machines correspondent ces adresses ?
indice: Compare avec ipconfig /all (passerelle par défaut et serveurs DNS).
= La <b>MAC</b> désigne le <b>prochain saut</b> local, la passerelle, parce que la couche 2 ne livre qu'au voisin direct. L'<b>IP</b> désigne la <b>destination finale</b>, le serveur DNS. C'est la différence couche 2 / couche 3 du cours : la MAC change à chaque saut, l'IP reste la même de bout en bout.
? {n24} **8b5.** IP b1) Taille de l'en-tête IP ? Longueur totale du paquet ?
indice: Internet Protocol → Header Length et Total Length.
= <b>En-tête = 20 octets</b> (sans options). La <b>longueur totale</b> dépend du nom demandé (en général 50 à 80 octets) : c'est en-tête IP (20) + en-tête UDP (8) + message DNS.
? {n24} **8b6.** IP b2) Champ Protocol de l'en-tête : numéro et type du protocole transporté ?
indice: Internet Protocol → Protocol.
= <b>17 = UDP</b>. Le DNS passe par UDP, parce que c'est rapide et qu'une petite question-réponse n'a pas besoin de la connexion TCP.
? {n26} **8b7.** UDP b1) Ports du client et du serveur ? Particularités ? Protocole applicatif ?
indice: User Datagram Protocol → Source Port, Destination Port.
= <b>Port destination = 53</b> : port réservé (bien connu, entre 0 et 1023) du DNS. <b>Port source</b> = un grand numéro choisi au hasard par le système (port éphémère, au-dessus de 1023, ex. 5xxxx ou 6xxxx). Il sert à reconnaître la conversation au retour. Protocole applicatif : <b>DNS</b>.
? {n24} **8b8.** UDP b2) Valeur du champ longueur de l'en-tête UDP ? Correspond-elle à l'en-tête IP ?
indice: UDP → Length, à comparer avec IP → Total Length.
= <b>Longueur UDP = longueur totale IP − 20</b> (l'en-tête IP). Elle inclut les 8 octets d'en-tête UDP et les données DNS. Exemple : IP 62 → UDP 42 → DNS 34 octets. Cela montre l'encapsulation : chaque couche contient la précédente.
```

```exercice VIII.3-c · Service DNS (requête puis réponse)
? {n25} **8c1.** Requête c1) Quel champ indique s'il s'agit d'une requête ou d'une réponse ?
indice: Domain Name System → Flags → Response.
= Le bit <b>QR (Response)</b> dans les Flags : <b>0 = requête (query)</b>, 1 = réponse. Pour une requête standard, les flags valent 0x0100.
? {n25} **8c2.** Requête c2) Information transportée dans le corps de la requête ? Type et classe ?
indice: DNS → Queries.
= Le <b>nom demandé</b> : www.fpbm.ma. <b>Type A</b> (adresse IPv4 ; tu peux aussi voir une requête AAAA pour IPv6) et <b>classe IN</b> (Internet, 0x0001).
? {n25} **8c3.** Requête c3) Identificateur de transaction ?
indice: DNS → Transaction ID.
= Un nombre sur 16 bits, en hexadécimal (ex. 0x3f2a), choisi par le client. Note ta valeur : tu en auras besoin pour la réponse.
? {n28} **8c4.** Réponse c1) Adresses MAC et IP attendues pour la réponse ? Vérifier.
indice: Filtre : dns.flags.response == 1, la réponse correspondante.
= Tout est <b>inversé</b> : <b>MAC source = la passerelle</b>, <b>MAC destination = ton PC</b> ; <b>IP source = le serveur DNS</b>, <b>IP destination = ton PC</b>. Les ports aussi sont inversés : 53 vers ton port éphémère.
? {n24} **8c5.** Réponse c2) Taille du paquet IP et du message UDP ? Est-elle plus grande que celle de la requête ?
indice: IP → Total Length et UDP → Length de la réponse.
= <b>Oui, elle est plus grande</b>. La réponse recopie la question, puis ajoute une ou plusieurs <b>réponses</b> (Answers : CNAME, adresse A…), parfois des serveurs d'autorité. Plus de contenu, donc des longueurs IP et UDP plus grandes.
? {n25} **8c6.** Réponse c3) Identificateur de transaction de la réponse ? Correspond-il à la requête ?
indice: DNS → Transaction ID de la réponse.
= <b>Identique</b> à celui de la requête. C'est ce qui permet au client d'associer chaque réponse à sa question, surtout quand plusieurs requêtes partent en même temps. UDP ne le fait pas pour lui, puisqu'il est sans connexion.
```

```exercice VIII.3-d · Requête HTTP GET (refais la capture avec http://neverssl.com)
? {n26} **8d1.** d1) Numéros de séquence et d'acquittement de l'en-tête TCP du GET ? Vérifier qu'ils correspondent aux valeurs attendues.
indice: Filtre : http.request.method == "GET". TCP → Sequence Number (relative) et Acknowledgment Number. Pour comprendre, regarde les 3 paquets avant : filtre tcp.stream == N (clic droit → Conversation Filter → TCP).
= En numérotation relative (celle de Wireshark par défaut) : <b>Seq = 1, Ack = 1</b>. Pourquoi : la poignée de main est SYN (Seq 0) → SYN-ACK (Seq 0, Ack 1) → ACK (Seq 1, Ack 1). Le SYN « consomme » 1 numéro, donc le premier octet de données du client porte le numéro 1, et le client attend l'octet 1 du serveur. En valeur brute (raw), ce sont de grands nombres aléatoires, les ISN, mais la logique reste la même.
? {n26} **8d2.** d2) Indicateurs d'état (flags) actifs de l'en-tête TCP ? Pourquoi ?
indice: TCP → Flags.
= <b>PSH et ACK</b> (0x018). <b>ACK</b> : le segment acquitte ce que le serveur a envoyé, ce qui est toujours le cas après la poignée de main. <b>PSH</b> : « pousse » les données vers l'application sans attendre, puisque le segment contient la requête complète.
? {n26} **8d3.** d3) Longueur de l'en-tête TCP et de la « charge » du message ?
indice: TCP → Header Length et \[TCP Segment Len\].
= <b>En-tête TCP = 20 octets</b> (32 si des options sont présentes). <b>Charge</b> = TCP Segment Len = la taille du texte de la requête GET (en général quelques centaines d'octets). Vérifie : Total Length IP − 20 (IP) − en-tête TCP = charge.
```

```exercice VIII.3-e · Réponse HTTP
? {n35} **8e1.** e1) Temps écoulé entre le GET et la réponse correspondante ?
indice: Différence des valeurs de la colonne Time, ou dans la réponse : HTTP → \[Time since request\].
= Lis-le dans ta capture : en général quelques dizaines à quelques centaines de millisecondes. Ce délai comprend l'aller-retour sur le réseau et le temps de traitement du serveur.
? {n26} **8e2.** e2) Le serveur répond-il avec un message HTTP ou avec un segment TCP ACK ?
indice: Regarde le paquet du serveur juste après le GET.
= Souvent, le serveur envoie <b>d'abord un ACK TCP seul</b> (sans données) pour accuser réception du GET, <b>puis</b> la réponse HTTP (200 OK). Parfois les deux sont combinés : la réponse HTTP porte elle-même le flag ACK. Dis lequel des deux cas tu observes.
? {n35} **8e3.** e3) Numéro de séquence émis par le serveur ? Correspond-il à la valeur attendue ?
indice: TCP du premier segment du serveur après le GET.
= <b>Seq = 1</b> (relatif) : c'est exactement la valeur de l'Ack envoyé par le client dans le GET (« j'attends ton octet 1 »). Et l'<b>Ack du serveur = 1 + longueur du GET</b> : il confirme avoir reçu tous les octets de la requête. C'est la règle du cours : ACK = numéro du prochain octet attendu.
? {n26} **8e4.** Réponse e1) Longueur de la « charge » dans l'en-tête TCP de la réponse HTTP ?
indice: TCP → \[TCP Segment Len\] du 200 OK. Si la page est grande : \[Reassembled TCP Segments\].
= C'est la taille de l'en-tête HTTP plus le début de la page. Si la page dépasse le <b>MSS (1460 octets)</b>, elle est découpée en <b>plusieurs segments</b> que Wireshark réassemble. C'est la segmentation de ton cours, vue en vrai.
? {n26} **8e5.** Réponse e2) Flags actifs de l'en-tête TCP de la réponse ? Pourquoi ?
indice: TCP → Flags du 200 OK.
= <b>PSH, ACK</b> (parfois <b>FIN, PSH, ACK</b> si le serveur ferme la connexion juste après). ACK : il acquitte la requête. PSH : il livre les données tout de suite. FIN : il ouvre la fermeture en 4 temps.
? {n35} **8e6.** Réponse e3) Prochain numéro de séquence attendu dans le message suivant émis par le client ?
indice: Calcule avec les valeurs relatives de ta capture, puis vérifie sur le paquet suivant du client.
= Le client continue sa propre numérotation : <b>Seq suivant du client = 1 + longueur du GET</b>, puisqu'il a déjà « consommé » ces octets. Son <b>Ack</b> vaudra <b>Seq du serveur + longueur de la réponse</b> : le prochain octet qu'il attend. Exemple : GET de 400 octets, réponse de 1200 octets → le client envoie Seq = 401, Ack = 1201.
```
