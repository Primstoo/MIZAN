  <h2>1. À quoi il sert</h2>
  <p>Cinq objectifs <span class="src">diapo 79</span> :</p>
  <ol>
    <li>illustrer le modèle de classes par un exemple concret ;</li>
    <li>faciliter la validation d’un diagramme de classes complexe en l’instanciant ;</li>
    <li>préciser des aspects imperceptibles dans le diagramme de classes ;</li>
    <li>exprimer une exception (cas particulier non généralisable) ;</li>
    <li>prendre une image du système à un moment donné.</li>
  </ol>
  <h2>2. Définition</h2>
  <div class="box retenir"><span class="tag">À savoir</span>
    <ul>
      <li>Un diagramme d’objets est une <b>instance</b> d’un diagramme de classes : des objets et les liens qui les unissent.</li>
      <li>C’est un graphe d’instances liées <b>statiquement</b>.</li>
      <li>Il est <b>conforme</b> au diagramme de classes qu’il illustre : il respecte ses contraintes (multiplicités comprises).</li>
      <li>Il <b>ne montre pas les interactions</b> entre objets (pas de messages).</li>
      <li>« Le diagramme de classes modélise les <b>règles</b>, le diagramme d’objets modélise des <b>faits</b>. »</li>
    </ul>
    <p class="src" style="display:inline-block">diapo 80</p>
  </div>
  <h2>3. Notation</h2>
  <p>Un objet est un rectangle à deux compartiments : le <b>nom de l’objet, souligné</b>, puis la liste des <b>attributs valorisés</b> (<code>nom = valeur</code>). Pas de compartiment d’opérations. <span class="src">diapo 81</span></p>

  <p>Règles sur les liens <span class="src">diapo 83</span> :</p>
  <ul>
    <li>les relations du diagramme de classes deviennent des <b>liens</b> ;</li>
    <li>la <b>généralisation n’a pas d’instance</b> : elle n’apparaît jamais dans un diagramme d’objets. Un objet de la sous-classe a directement tous les attributs hérités ;</li>
    <li>un lien se dessine comme une relation ; s’il a un nom, ce nom est <b>souligné</b> ;</li>
    <li>on ne représente <b>pas les multiplicités</b>.</li>
  </ul>

  <h2>4. L’objet composite <span class="src">diapos 85–86</span></h2>

  <h2>5. Recommandations du prof <span class="src">diapo 87</span></h2>
  <ul>
    <li>Ne l’utiliser que pour clarifier des structures complexes du diagramme de classes.</li>
    <li>Tous les objets possibles n’ont pas à y figurer.</li>
    <li>Ne pas mélanger classes et objets dans un même diagramme.</li>
    <li>Il peut servir de base à un diagramme d’interaction (séquence ou collaboration).</li>
  </ul>
  <h2>6. Méthode pour en construire un à l’examen</h2>
  <ol>
    <li>Pars du diagramme de classes (ou construis-le d’abord).</li>
    <li>Pour chaque élément du scénario, crée un objet <code>nom : Classe</code> d’une classe <b>concrète</b> (jamais une classe abstraite).</li>
    <li>Remplis les attributs avec des valeurs plausibles, y compris les attributs hérités.</li>
    <li>Trace un lien pour chaque instance d’association. Garde le losange si c’est une composition, comme le prof le fait (diapo 89).</li>
    <li>Vérifie les multiplicités : si une classe exige <code>1</code> lien, chaque objet doit l’avoir.</li>
  </ol>
  <div class="box piege"><span class="tag">Pièges</span>
    <ul>
      <li>Nom d’objet non souligné.</li>
      <li>Triangle d’héritage dans un diagramme d’objets.</li>
      <li>Multiplicités écrites sur les liens.</li>
      <li>Objet d’une classe abstraite (<code>p : Personne</code> si Personne est abstraite).</li>
      <li>Objet sans un lien obligatoire (multiplicité 1 non respectée) : le diagramme n’est plus conforme.</li>
      <li>Compartiment d’opérations ajouté : un objet n’en a pas.</li>
    </ul>
  </div>
